## 1. 目的与边界

`FR3-FR5详细需求.md` §4/§5 回答「**有哪些规则、各自做什么**」；本文回答「**这些规则怎么被安全地执行**」。

| 在范围内 | 不在范围内 |
|---|---|
| 规则数据结构扩展（执行所需字段） | 具体规则的业务清单（见 FR3-FR5） |
| 依赖矩阵与冲突阻断 | 集成（更新/驱动/语言包，见 `集成规范.md`） |
| 执行上下文与跳过语义 | 无人值守 XML 生成（见 `无人值守规范.md`） |
| 应用顺序、幂等、失败处理 | 挂载实现细节（见引擎规范 §7） |
| 验证方法与可逆性记录 | 预设文件格式（见 `预设与配置契约规范.md`） |

**风险前提**：本阶段的输出直接决定镜像能否安装、功能是否完整。因此设计取向是「**宁可少改，不可改坏**」——不确定的组合阻断，不满足上下文的项跳过且必须可见。

## 2. 规则数据模型（在 `rules.schema.json` v1.0 上扩展）

### 2.1 现有字段（保持不变）

`id` / `name` / `nameEn` / `domain` / `group` / `description` / `warning` / `level` / `defaultOn` / `presets` / `requires` / `conflicts` / `order` / `applicable` / `actions`。

### 2.2 需新增字段（**向后兼容增补**，`schemaVersion` 保持 1.0）

> 这些字段全部**可选**，现有规则文件无需改动即可通过校验；规则内容批次用 `packVersion` 单独标识。JSON Schema 无法表达的约束（如「高风险必须有 verify」）由加载器做语义校验，见 §8。

| 字段 | 类型 | 用途 | 缺失时 |
|---|---|---|---|
| `context` | array：`offline`/`firstBoot`/`online` | 明确该规则可在哪些上下文执行（与 `actions[].mode` 取交集）；`online` 仅为兼容规则库而保留，本工具一律跳过（§3.4） | 取 `actions[].mode` 的并集 |
| `verify` | object | **如何证明生效**（见 §6） | 视为无验证，仅警告（高风险项不允许缺失） |
| `reversible` | boolean | 是否可逆（见 §7） | 默认 `false`（保守） |
| `recovery` | string | 不可逆项的影响面与恢复方式（人可读） | 缺失时 `reversible=false` 视为「不可逆且无恢复说明」→ 高风险项拒绝启用 |
| `params` | object | 可参数化项（如超时秒数、保留天数） | 无参数 |
| `minEngine` | string | 需要的最低程序版本（语义变化时防止旧版误用） | 不限制 |
| `estimatedBytes` | integer | 预估释放空间（FR5 展示用） | 不展示 |

> **高风险项的硬要求**：`level=high` 必须提供 `verify` 与 `recovery`（`reversible=false` 时），否则加载即判规则库无效（`RULEPACK_INVALID`）。这条用于防止「危险规则偷偷进库却没有验证手段」。

### 2.3 规则示例

```json
{
  "id": "FR5-OP-T64",
  "name": "禁用系统还原",
  "domain": "FR5",
  "group": "系统保护",
  "level": "high",
  "context": ["offline"],
  "requires": [],
  "conflicts": ["FR5-OP-T65"],
  "order": 320,
  "applicable": { "osMin": 22000, "imageFlags": ["offline"] },
  "actions": [
    { "type": "regWrite", "hive": "SOFTWARE", "key": "Microsoft\\Windows NT\\CurrentVersion\\SystemRestore",
      "value": "DisableSR", "regType": "REG_DWORD", "data": 1 }
  ],
  "verify": { "type": "regValue", "hive": "SOFTWARE",
              "key": "Microsoft\\Windows NT\\CurrentVersion\\SystemRestore",
              "value": "DisableSR", "expected": 1 },
  "reversible": true,
  "recovery": "重新启用系统保护并设置还原点即可恢复，不影响已装系统"
}
```

## 3. 执行上下文（已决策 D2：跳过但必须可见）

### 3.1 三类上下文

| 上下文 | 含义 | 本工具的支持 |
|---|---|---|
| `offline` | 对挂载的映像执行（DISM/wimlib + 离线注册表） | **主路径**，默认 |
| `firstBoot` | 写入无人值守脚本，首次登录时执行 | 由 Unattend 阶段注入（`无人值守规范.md` §8） |
| `online` | 对正在运行的系统执行 | **不支持**（本工具只处理离线映像；保留定义供规则库兼容） |

### 3.2 有效上下文的推导

```
effectiveContext = context（缺省取 actions[].mode 并集）
                 ∩ applicable.imageFlags（若声明）
                 ∩ 当前执行环境（offline / firstBoot）
```

### 3.3 不满足时：跳过 + 可见（不静默、不失败）

| 处理 | 规定 |
|---|---|
| 行为 | 跳过该规则，标 `skipped`，**不应用、不报错** |
| 记录 | `event=rule_skipped rule=<id> reason=context_unsatisfied required=<ctx> current=<ctx>` |
| 汇总 | 阶段结束在结果中列出「因上下文不满足跳过 N 项」及规则名；GUI 在阶段详情可展开；CLI 在 JSON 结果的 `skippedRules[]` 输出 |
| 严格模式 | `TaskConfig.slim.strictContext=true` 时改为失败（`RULE_CONTEXT_UNSATISFIED`），供需要「一项不落」的用户使用。GUI 设置页的同名开关只是「新建任务时的默认值」（`settings.defaults.*`），运行时以 TaskConfig 为准（配置规范 §3.5） |

> 理由：从模板导入的预设常含少量在线项，若一律失败，任务会因「一条无关规则」整体不可用；但静默跳过会让用户误以为已生效。折中方案是**跳过 + 明确可见 + 可选严格**。

### 3.4 `online` 规则的处理

- 规则库中 `online` 规则在本工具中**一律跳过**，并在「不支持项」汇总中单列（区别于「上下文不满足」），提示「该规则需要在线系统，本工具不支持」。
- 不允许静默当作离线规则执行（离线改在线 hive 会造成不可预期的行为）。

## 4. 依赖矩阵（已决策 D1：手写约束 + 实测数据补全）

### 4.1 两个来源

| 来源 | 内容 | 谁维护 | 冲突时 |
|---|---|---|---|
| **硬约束**（手写） | 包/能力/功能之间的「必需」关系与禁止组合，可评审、可解释 | 人工评审后入库 | **以手写为准**，实测数据冲突记 `WARN matrix_conflict` |
| **观测数据**（实测生成） | 从映像 inventory 导出「包 → 提供的能力」映射、包体积、依赖计数 | 由脚本对固定样本生成 | 仅用于**补全与提示**，不单独用于阻断 |

### 4.2 矩阵文件：`rules/dependency-matrix.json`

```json
{
  "schemaVersion": "1.0",
  "generatedFrom": { "build": "26100.6508", "edition": "professional", "generatedAt": "..." },
  "capabilities": [
    { "name": "Language.Basic~~~zh-CN~0.0.1.0", "providedBy": ["Package_for_...~31bf3856ad364e35~amd64~~26100.1.1.0"], "requiredByRules": ["FR4-SL-C03"] }
  ],
  "blockedCombos": [
    { "remove": ["FR4-SL-A07"], "breaks": ["Windows Search 体验"], "severity": "warning", "evidence": "实测：删除后搜索无结果" }
  ]
}
```

- `blockedCombos` 的 `severity`：`block`（拒绝执行并说明）或 `warning`（允许但二次确认）。

### 4.3 阻断判定（执行前统一做一次）

```
① requires 未满足（规则未被选中）           → 阻断该项，提示「需同时选择 X」
② conflicts 命中（互斥规则同时选中）        → 阻断，提示二选一
③ blockedCombos severity=block 命中        → 阻断，说明影响面
④ 高风险项未确认                            → 阻断该项（不是整任务）
⑤ 传递依赖存在环                            → 规则库无效（RULEPACK_CYCLIC）
```

- 阻断是**逐项**的：只去掉有问题的项并告知原因，不因为一条冲突让整个阶段失败。
- 阻断结果写入 `rules-report.json`（§8），用户可在执行前查看。

## 5. 应用顺序与幂等

### 5.1 顺序

```
按 order 升序 → 同 order 内按 requires 拓扑排序 → 再按 id 字典序（保证可复现）
```

- `requires` 指向的规则若未被选中 → 按 §4.3 ① 阻断。
- 顺序确定后**不因用户勾选顺序变化**（同一预设必然产生同一执行序列）。

### 5.2 幂等

- 每条规则重复执行不得产生副作用差异：
  - 注册表写入：覆盖为同值；
  - 包/能力移除：已不存在视为成功（`already_absent`）；
  - 服务启动类型：重复设置同值；
  - 文件删除：不存在视为成功。
- 幂等性是**规则入库的准入条件**：非幂等规则必须提供 `guard`（前置条件检查），否则拒绝入库。

### 5.3 单条失败的处理

| 规则等级 | 失败处理 |
|---|---|
| `high` | **中断阶段**，`UNMOUNT /Discard`，不提交任何修改（避免半套高风险改动） |
| `medium` | 记 `ERROR`，继续执行后续规则，阶段结束时汇总失败项；**阶段态仍为 `succeeded`**（不是新状态），但 `rules-report.json` 的 `summary.failed>0`，任务退出码 1（完成但有警告），并记 `stage_finished result=partial` |
| `low` | 记 `WARN`，继续 |

> 说明：阶段/任务的状态取值是封闭集合（术语表 §2.2），**没有「部分成功」这个状态值**。所谓「部分成功」只是「阶段 `succeeded` + 存在失败明细 + 退出码 1」的口语说法，不得写进 `status` 字段。

- `TaskConfig.slim.strictFail=true` 时任何等级失败都中断（供追求「一项不落」的用户）。

## 6. 验证（`verify`）

### 6.1 支持的验证类型

| 类型 | 判据 | 适用 |
|---|---|---|
| `regValue` | 键值等于期望（含类型） | 注册表类 |
| `regAbsent` | 键或值不存在 | 删除类 |
| `packageAbsent` | `DISM /Get-Packages` 中不存在匹配项 | 移除包 |
| `appxAbsent` | 预置 Appx 列表中不存在 | 移除 Appx |
| `capabilityAbsent` | 能力列表中不存在 | 移除能力 |
| `fileAbsent` | 路径不存在（支持通配） | 删文件 |
| `serviceStart` | 服务 Start 值等于期望 | 服务类 |
| `commandExit` | 指定只读命令返回 0 | 其他 |

### 6.2 验证时机

- **单条验证**：应用后立即验证（低成本项）；
- **阶段收尾验证**：`unmount` 之前对所有 `high` 项与随机抽样的 10% 其他项统一验证（批量命令，减少开销）；
- 校验不通过 = 该项失败，按 §5.3（单条失败的处理）处理，`high` 项直接导致丢弃挂载。

### 6.3 为什么必须验证

「命令返回 0」不等于「改动生效」——例如包名匹配到 0 个包时 `DISM` 也可能返回成功。没有 `verify` 的规则无法区分「做成了」与「什么都没做」。

## 7. 可逆性与回滚（已决策 D3：仅高风险 + 不可逆项）

### 7.1 记录范围

| 范围 | 是否记录 `reversible`/`recovery` |
|---|---|
| `level=high` | ✅ 必须 |
| `reversible=false` 的任意等级 | ✅ 必须 |
| 其余 | 不要求（默认 `reversible=true` 视为「丢弃挂载即可还原」） |

### 7.2 回滚机制

| 层级 | 手段 |
|---|---|
| 阶段内失败 | `DISM /Unmount-Image /Discard` —— 整段修改丢弃，映像回到挂载前状态 |
| 提交后发现系统异常 | 依赖 `rules-report.json` 定位可疑规则，用户重建镜像并取消该项 |
| 不可逆项（如 `ResetBase`） | **无回滚**；执行前二次确认，文案必须说明「该操作不可撤销」 |

### 7.3 执行清单留痕

- 阶段开始时记录「将要应用」的规则清单（id + 名称 + 等级），阶段结束时记录「实际应用/跳过/失败」；
- 清单写入 `rules-report.json` 并随产物 `readme.txt` 摘要（前 20 项 + 总数），便于事后追溯。

## 8. 规则包版本与兼容

| 项 | 规定 |
|---|---|
| 规则包版本 | 数据结构用 `schemaVersion`（当前 1.0，增补字段向后兼容）；内容批次用 `packVersion`（语义化版本） |
| 引擎兼容 | 每条规则可声明 `minEngine`；低于该版本的程序**跳过并提示**，不执行 |
| 规则包校验 | 加载时校验 Schema、id 唯一、`requires`/`conflicts` 指向存在、无环、高风险项含 `verify`/`recovery`；失败即 `RULEPACK_INVALID`，**不使用部分加载** |
| 校验落地 | 实现见 `infrastructure/rules/loader.py`（`load_library`）；`scripts/check_rules.py` 可单独跑；环检测单独报 `RULEPACK_CYCLIC` 并在消息里给出环路 |
| 升级 | 规则包随程序发布；用户不可在线更新（与工具信任根策略一致） |
| 变更可见 | 规则删除或语义变化必须在 CHANGELOG「已知限制」中列出，避免旧预设静默失效 |

## 9. 预设与规则的绑定（已决策 D4：按项）

- `TaskConfig.slim` / `TaskConfig.optimize` 的形状与预设一致（配置规范 §4.1/§4.2）：`{ "origin": {...}, "ruleIds": [...], "params": {...} }`，**不是**按「Appx/包/能力」分类的删除清单：

```json
{
  "origin": { "presetId": "slim-safe", "presetVersion": "1.2", "snapshottedAt": "2026-10-30T12:00:00+08:00" },
  "ruleIds": ["FR4-SL-A01", "FR4-SL-A07", "FR4-SL-C03"],
  "params": { "FR5-OP-C12": { "keepDays": 7 } }
}
```

- 早期草案的 `items.appx.remove[]` / `packages.remove[]` / `capabilities.remove[]` 分类清单**已废弃**（无法做未知规则拒绝与 `verify` 追溯），迁移时把裸名称解析为 `ruleId`。

- 未知 `ruleId` → **拒绝导入**并列出缺失项（与配置规范 §4.2 一致），不允许静默丢项。
- 规则库升级后旧预设仍可用：只要这些 `ruleId` 仍存在且 `minEngine` 满足；语义变化由规则包 `packVersion` 与 CHANGELOG 说明。

## 10. 执行流程（阶段内）

```
1. 解析选项 → 得到 ruleIds[]
2. 加载规则包 → 校验（RULEPACK_*）
3. 上下文过滤（§3）→ skipped/online-unsupported 汇总
4. 依赖与冲突判定（§4.3）→ 逐项阻断
5. 高风险确认检查 → 未确认即阻断该项 + 审计事件
6. 排序（§5.1）
7. 挂载映像（ReadOnly=false）
8. 逐条 apply → verify（§6）
9. 阶段收尾批量验证（high 全量 + 10% 抽样）
10. 卸载并提交（全部通过）或丢弃（high 失败 / 严重错误）
11. 写 rules-report.json + 事件
```

- 挂载、卸载、残留清理遵循引擎规范 §7；取消遵循编排规范 §8（保留中间产物、退出码 3）。
- 全流程记 `stage=Slim|Optimize`，规则级事件带 `rule=<id>`。

## 11. 报告文件：`rules-report.json`

`{work}\<task>\reports\rules-report.json`：

```json
{
  "taskId": "7f3a1c02",
  "stage": "Slim",
  "rulePack": { "schemaVersion": "1.0", "packVersion": "1.4.0" },
  "startedAt": "...", "finishedAt": "...",
  "summary": { "selected": 12, "applied": 9, "skipped": 2, "failed": 1, "blocked": 0 },
  "items": [
    { "ruleId": "FR4-SL-A01", "status": "applied", "verify": "pass", "duration": 1.2 },
    { "ruleId": "FR4-SL-A07", "status": "skipped", "reason": "context_unsatisfied" },
    { "ruleId": "FR5-OP-T64", "status": "applied", "verify": "fail", "error": "regValue mismatch" }
  ]
}
```

- 该文件是排查「镜像为何少了某功能」的第一手依据，必须保留到任务被清理。
- 失败项必须含 `error` 与 `verify` 结果；跳过项必须含 `reason`。

## 13. 验收标准

1. **上下文跳过可见**：预设含 2 条 `online` 规则 + 1 条 `firstBoot` 规则 → 全部跳过，`rules-report.json` 的 `skipped` 为 3 且 `reason` 正确；CLI JSON 输出 `skippedRules[]`；开启严格模式后改为失败 `RULE_CONTEXT_UNSATISFIED`。
2. **依赖阻断**：只选 `requires` 未满足的规则 → 该项被 `rule_blocked reason=requires_missing`，其余规则正常执行，阶段不整体失败。
3. **冲突阻断**：同时选两条 `conflicts` 规则 → 两条都被阻断并提示二选一，报告含 `blocked`。
4. **禁止组合**：命中 `blockedCombos severity=block` → 阻断并给出 `evidence`；`warning` 级 → 允许但需二次确认。
5. **高风险未确认**：`level=high` 且未确认 → 该项阻断 + 审计事件，其他项照常。
6. **顺序稳定**：同一预设勾选顺序打乱 → 实际执行序列（按 `order`+拓扑+id）完全一致。
7. **幂等**：连续两次应用同一规则集 → 第二次全部 `already_absent`/同值写入，`applied` 计数一致且无错误。
8. **高风险失败丢弃**：注入一条必然失败的 `high` 规则 → 阶段卸载 `/Discard`，映像无任何修改残留，退出码 2。
9. **中风险失败继续**：`medium` 规则失败 → 继续执行其余项，阶段结束 `failed=1`、退出码 1。
10. **验证生效**：包名匹配 0 个包时 `DISM` 返回 0 → `verify` 判失败（`packageAbsent` 未满足），不被误判为成功。

12. **报告完整**：执行 10 条规则后 `rules-report.json` 的 `items` 覆盖全部选中项，`summary` 各计数与明细一致。
