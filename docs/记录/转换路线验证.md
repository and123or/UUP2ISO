# UUP → ISO 转换路线验证（FR3）

> 分类：记录（实测事实） ｜ 目录：`docs/记录/`
> 状态：**已用真实数据实测**（2026-10-16）。本文替代此前"必须先完成 PSF 差分 Spike"的假设——
> 该假设**未经实测**，实测结果表明它对本样本不成立。
> 样本：UUP dump list id `94b8c5e5-d0ea-41c1-937c-c5ce99ad518b`（Windows 11, version 24H2 (26100.6508)，amd64，en-us）。

## 1. 结论（实测）

| 问题 | 实测结论 |
|---|---|
| UUP 集里有 `.psf` 差分文件吗？ | **没有**。195 个文件 = 165 `.cab` + 27 `.esd` + 2 `.msu` + 1 `.wim`，`.psf` 数量为 **0** |
| 媒体骨架（引导文件）需要另外获取吗？ | **不需要**。它就在 UUP 集内的 `professional_en-us.esd` 里 |
| 需要"重建 install.wim"吗？ | **需要聚合**：本样本没有 `.psf`，所以**不需要差分重建**；但没有任何 ESD 能单独充当 `install.wim`，必须经组件聚合（§5 已用两条独立证据确证） |
| 转换的关键外部工具 | `wimlib-imagex`（读取/提取/导出）与 `oscdimg`（封装 ISO） |

**因此 FR3.1 的 PSF 差分对本样本不是必经路径**：不存在需要应用差分的文件。
PSF 相关能力仍可能在其它构建/其它 UUP 源中出现，但**不应作为原味 ISO 的前置**。

## 2. UUP 集的实际内容

- `.cab`：FOD / 语言特性 / 更新包等（如 `Microsoft-Edge-WebView-FOD-Package-amd64.cab`）。
- `.esd`：**LZMS 压缩的 WIM 容器**，其中 `professional_en-us.esd` 是组装好的成品。
- `.msu` / `Edge.wim`：更新包与 Edge 映像。

## 3. 成品 ESD 的结构（`wimlib-imagex info`）

```
Image Count: 3      Compression: LZMS      Boot Index: 2
Index 1  Windows Setup Media                                  （媒体骨架，959 个文件）
Index 2  Microsoft Windows Recovery Environment (amd64)       （boot.wim 内容）
Index 3  Windows 11 Pro                                        （install 映像）
```

`Boot Index: 2` 指明 boot.wim 应指向索引 2（WinRE），即 `sources\boot.wim` 的来源。

## 4. 媒体骨架：提取即可获得（实测命令与结果）

```powershell
wimlib-imagex apply professional_en-us.esd 1 <ISO暂存目录>
```

- 实测：**1.8 秒**完成，`exit=0`。
- 落盘校验（全部命中）：

| 路径 | 结果 |
|---|---|
| `boot\etfsboot.com` | 4096 字节 |
| `efi\microsoft\boot\efisys.bin` | 1474560 字节 |
| `bootmgr` | 473364 字节 |
| `bootmgr.efi` | 2744752 字节 |
| `boot\bcd` | 16384 字节 |
| `sources\` | 目录存在 |

顶层条目：`boot`、`efi`、`sources`、`support`、`autorun.inf`、`bootmgr`、`bootmgr.efi`、`setup.exe`。

非管理员运行时 wimlib 会警告无法恢复 1047 个文件的安全描述符；对媒体内容无影响。

## 5. 仍然缺少的零件（实测更正）

媒体骨架里 `sources\` **只有 `setup.exe`，不含** `boot.wim` 与 `install.wim|esd`。后续实测结果如下：

| 步骤 | 实测结果 |
|---|---|
| 提取媒体骨架（映像 1） | ✅ `wimlib-imagex apply <esd> 1 <目录>`，**1.8 秒**，引导文件全部落盘 |
| 生成 `sources\boot.wim`（映像 2） | ✅ `wimlib-imagex export <esd> 2 --compress=LZX --check <目标>`，**19.4 秒**，458.3 MB，`Image Count: 1`、`Name: Microsoft Windows Recovery Environment (amd64)` |
| 生成 `sources\install.wim`（映像 3） | ❌ **失败**：`wimlib-imagex export` 报 **exit 55「A file resource needed to complete the operation was missing from the WIM」** |

### install 映像不能单独导出：根因是"分片（非独立）映像"

`wimlib-imagex verify` 会给出关键判据——**"if this WIM file is not standalone, use the --ref option"**。
对同一构建（26100.6508）的多个 ESD 实测：

| ESD | 大小 | `verify` | 说明 |
|---|---|---|---|
| `Microsoft-Windows-Client-Desktop-Required-Package.ESD` | 777.1 MB | **0（通过）** | 独立文件：1 个映像、2547763497 字节、LZMS |
| `professional_en-us.esd` | 528.1 MB | **55** | 非独立：列出 3 个映像（含 15.3 GB 的 Windows 11 Pro 树），但数据在别处 |
| `core_en-us.esd` | 558.8 MB | **55** | 非独立：同样列出完整树，导出/校验都失败 |

**结论**：UUP 集中的 edition ESD（`core_*` / `professional_*` 等）是**分片形态**——
它们仅"列出"完整文件树，真实数据分散在配套 ESD 中，因此不能单独 `apply`/`export`。

> 这也解释了上一版"exit 55"的误判：当时我选用的 `professional_en-us.esd` **本身就不是独立文件**，
> 失败并非路线不通，而是素材选错 + 缺少独立性校验。

组装前**必须先做独立性校验**，否则只能拿到难以理解的 `exit 55`。该判据已实现进 `SourcesAssembler`：
先 `VerifyAsync`，非独立即报"映像不是独立文件，无法取出映像数据……请改用该构建中可独立校验的映像，
或先完成分片合并"，并且**不执行任何重活**。

另经检查：`Microsoft-Windows-EditionPack-Professional-Package.ESD`（147.5 MB）的影像是
**按哈希命名的组件清单**（`\amd64_accessibility_<hash>\...` + `.manifest`），不是完整文件系统树；
其 `export` 本身可用（147.5 MB → 221.5 MB 的 LZX WIM，9.5 秒，`Image Count: 1`、`Name: Edition Package`），
说明工具能力没问题。

### 已确认：独立映像同样是组件包，install.wim 必须经组件聚合

对上轮遗留问题做了收尾验证——`Microsoft-Windows-Client-Desktop-Required-Package.ESD`（777.1 MB，`verify` 通过）
解包查看后的顶层结构：

```
\amd64_adaptivecards-xamlcardrenderer_31bf3856ad364e35_10.0.26100.1_none_d7c7a47386e51e49\
    Windows.Internal.AdaptiveCards.XamlCardRenderer.dll
\amd64_adaptivecards-xamlcardrenderer_..._d7c7a47386e51e49.manifest
\amd64_dual_1394.inf_..._a4d621f9df98c6a4\1394.inf, 1394ohci.sys
\amd64_desktop_shell-search-srchadmin_..._9a16eceba6a498e4\srchadmin.dll, srchadmin.dll.mun
```

即**同样是按哈希命名的 CBS 组件清单**（`\amd64_<name>_<hash>\…` + `.manifest`），**不是完整文件系统树**。

**结论（已用两条独立证据确证）**：该构建中**没有任何 ESD 能单独充当 `sources\install.wim`**。
无论分片 ESD 还是独立 ESD，提供的都是组件包形态；install 映像必须经**组件聚合**得到，
而其映射与顺序规则**尚未验证**。按《项目计划》§11，不得凭猜测实现。

### 追加取证：组件包不能靠 "apply + capture" 聚合

对上述结论做了一次有界实验（`Microsoft-Windows-EditionPack-Professional-Package.ESD`，147.5 MB）：
`wimlib-imagex apply <esd> 1 <空目录>` 成功（13.1 秒），但落盘结果是：

- **5463 个按哈希命名的散包目录**（`amd64_<name>_<hash>/…` + `.manifest`）；
- **不存在 `\Windows`、`\Program Files`、`\Windows\System32`**。

即"把组件包解包再 `capture` 成 install.wim"**不可能**产出可用的 Windows 树——
组件包是 CBS 增量单元，需要**基础映像**作为落点。

因此 install 映像的合成路径只有两条，且都需要外部决定：
1. 复用已验证的转换器（`uup-converter-wimlib` / UUP Media Creator）——它内置了聚合与映射规则；
2. 先确定该构建可用的**基础映像来源**（本样本的 edition ESD 均非独立文件，无法直接充当基准）。

这也说明：**这不是"再花点时间就能自己写出来"的工作**，而是缺少已验证的映射规则与基准素材。

因此 `Convert` 阶段的现状是**部分实现**：媒体骨架与 `sources\boot.wim` 可真实产出；
`install.wim` 在导出阶段**显式失败并说明需要组件聚合**（不是笼统的"未实现"）。

## 6. 对既有结论的更正

> 2026-10-31 同步修订：§1 的「是否需要重建 install.wim」一行原写「本样本已给出组装好的映像，无需重建」，与 §5 的实测更正（没有任何 ESD 能单独充当 `install.wim`）冲突；本次只把 §1 对齐到 §5，**未改动任何实测数据与命令输出**。原 §6 的引用同时修正为 FR/WP 编号（原文引用了一个不存在的章节号，并把《项目计划》的前置要求指向了错误的章节）。

- 《需求分析》FR3.1 与《项目计划》WP3-T2 曾把 PSF 差分列为 MVP 前置；**基于本样本的实测，该前置不成立**
  （UUP 集中没有 `.psf`），建议降级为"特定构建/特定源才需要"的按需能力。
- **但 install 映像的组件聚合是真实存在且未验证的环节**：它不是 PSF 差分，而是把多个组件 ESD
  合成完整 install 映像。按《项目计划》§11「禁止未经验证的自实现进入 MVP」，该环节需要先做验证
  或复用已验证的转换器（`uup-converter-wimlib` / UUP Media Creator），不得凭猜测实现。
- 之前以"PSF 未完成 Spike"为由把 `Convert` 阶段做成显式失败：现在应改为——媒体骨架与 `boot.wim`
  可以真实产出；`install.wim` 合成在聚合规则未验证前显式失败并说明原因。
